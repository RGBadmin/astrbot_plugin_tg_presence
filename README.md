# 角色 Telegram 存在感（tg_presence）

让 Telegram 上的角色像真人一样"有自己的生活痕迹"：自己发动态到频道、换头像、对消息打表情，并且**记得你发过的每一张图** —— 哪怕图早就不在上下文里了。

行为能力全部注册为 **LLM 工具**，由角色自主决定何时使用；发动态和换头像同时保留手动指令入口。

> 仅支持 Telegram 平台。需要 AstrBot >= 4.26，python-telegram-bot >= 22.7（换头像所需，其余功能不受此限）。

---

## 能做什么

| 能力 | 说明 | 入口 |
|---|---|---|
| 发动态 | 往指定频道发一条动态，可带配图。频道是真正的时间线，能往回翻、有推送 | LLM 自主 / `/moment` |
| 换头像 | 从候选目录里挑一张 JPEG 换上 | LLM 自主 / `/avatar` |
| 表情回应 | 给对方刚发的消息打一个表情 | LLM 自主 |
| 图片记忆 | 把上下文里的图片换成可检索的文字，省 token 又不失忆。见 [图片记忆](#图片记忆) | LLM 自主 / `/vision` |
| 发照片 | 从自己的相册里挑一张发给对方，也能重发聊过的旧图。见 [发照片](#发照片) | LLM 自主 / `/photo` |

另有 `/presence` 查看状态（已发动态数、各项冷却剩余、图片存档统计）。

### 为什么用频道而不是改简介

Telegram bot 的「简介」（`setMyDescription`）**只在你还没和它对话过时显示一次**，聊过之后永远看不到。角色改了也没人看得见，所以这个功能已被移除。

频道则是真正的时间线：一条条累积、能往回翻、有推送通知 —— 行为上接近朋友圈/空间说说。

### 配图从哪来

发动态时按这个顺序取图：

1. **当前消息里附带的图片**（优先）—— 你发 `/moment 今天天气真好` 并在同一条消息里附几张图，这些图就是这条动态的配图。角色自主调用时同理：你发张图说「帮我发到频道」，她调 `post_moment`，那些图会被带上
2. **配图目录**（回退）—— 消息里没带图时，才按 `category` 从 `moment_photo_dir` 里随机挑一张

一次最多 10 张（Telegram 媒体组上限）。单张走 `sendPhoto`，多张走 `sendMediaGroup`。
正文超过 1024 字符时塞不进图片 caption，插件会先发图、再补一条纯文字。

附带的图片会被拷进插件数据目录长期保存 —— 平台的临时目录会被清理，而历史动态注入可能很久以后才读它。

## 图片记忆

### 要解决的问题

AstrBot 把图片以 base64 data URL **永久写进对话历史**，之后每一轮都原样重发。几十张之后，上下文里全是图片，既烧 token 又稀释注意力 —— 模型的有效注意力被一堆不相关的旧图分走了。

但直接删掉图片又不行：对方会说「昨天那张」「黑丝那张」，角色得认得出来。

所以这里的做法是 **把图片换成文字，留在时间线上**。

### 两层描述

一张图存两份文字，用途不同：

| 层 | 谁写的 | 长度 | 内容 | 存在哪 |
|---|---|---|---|---|
| **目录层** | 主模型（角色自己） | 一句话 | 她的视角和当时的语境：「阿泽昨天加班时拍的」 | `state.json` 的 `photo_desc` |
| **细节层** | 独立视觉模型 | 几百字 | 客观画面：构图、衣着材质颜色、物品、文字、光线 | `vision.json` |

**目录层**跟正文一次生成 —— 上下文里出现没描述过的图时，插件注入一段请求，角色在回复末尾附 `<img_note id="3">…</img_note>`，插件抽走存档并从要发出去的内容里剥掉，对方看不到。**不额外调模型**，而且此刻她正看着图、也知道当时在聊什么，写出来的话带着她自己的说法。

**细节层**在图片首次进入上下文时**异步**调视觉 API 解析，不阻塞回复。这套 API 配置**在插件里独立填**（格式 / 地址 / Key / 模型 ID / 系统提示词 / 最大输出长度 / 流式开关），不走 AstrBot 的服务提供商 —— 主对话模型贵、这个便宜，本来就不该共用一套配置，也不该让它出现在对话模型的候选列表里。支持 **OpenAI 兼容、Anthropic 原生、Gemini 原生**三种接口格式，挑个便宜的多模态模型即可。

两层的价值在于**信息类型不同，不只是详略不同**。他说「昨天加班那张」走目录层，说「有咖啡杯那张」走细节层。而且能跨层组合：「加班 咖啡杯」——「加班」在目录、「咖啡杯」在细节，照样命中。

### 检索

| 工具 | 做什么 | 代价 |
|---|---|---|
| 看占位 | 折叠后的 `[图片 #3 · 07-31 14:30 · 阿泽拍的，穿黑丝踩高跟 · 已折叠]` 就在对话里，读一眼就认出来 | 零 |
| `find_photo` | 按关键词 + 日期搜存档，两层一起搜 | 一次工具调用 |
| `inspect_photo` | 查某张图的画面细节，**只回文字** | 一次工具调用 |
| `recall_photo` | 把原图整个塞回上下文重新看 | 一张图的 token |

顺序是有讲究的：占位就在眼前，不需要检索；`find_photo` 查的是存档，不依赖上下文，所以 `llm_compress` 压掉占位后它照样能找到；`inspect_photo` 回答「那张图里有什么」而不用重新传图，比 `recall_photo` 便宜一个数量级。

**候选不止一张时，提示词要求她反问是哪张，而不是自己挑一张当成就是那张。**

### 上下文瘦身

`max_context_images` 设成正数后，只保留最近 N 张真图，更早的换成文字占位。

> ⚠️ **折叠会写回对话历史，不可逆。** 但图片在首次进入上下文时就已经存到 `context_photos/` 下了，原图不会丢，`recall_photo` 随时能取回。

默认 `0`（不折叠）。**建议先验证目录层工作正常再开** —— 见下面的验证顺序。

## 发照片

角色能主动发照片给对方，图从两处来：

| 来源 | 编号 | 说明 |
|---|---|---|
| **相册目录** | `g123` | `gallery_dir` 下的图，扫描登记 + 视觉索引后可按画面内容检索 |
| **聊过的旧图** | `#3` | 之前出现在对话里的图（`context_photos/`），随时能重发 |

动态的配图会在发出时自动登记进相册库，所以也能被翻到、被重发。

### 工具

| 工具 | 做什么 |
|---|---|
| `browse_gallery(keywords, folder)` | 在相册里翻，返回候选 `g123` 列表。不带关键词就是随手翻翻 |
| `send_photo(photo_id, caption)` | 发出去。`g123` 是相册里的，`#3` 是聊过的旧图 |

检索结果里**最近发过的排在最后**，避免反复发同一张。

### 建索引

上万张图不可能塞进上下文，得先建一份可检索的索引。分两步，都能中断续跑：

```
/gallery scan          扫目录登记路径（不调 API，几秒到几十秒）
/gallery index 50      给还没描述的图跑视觉 API，一次 50 张
/gallery index 50      ……重复，直到跑完
/gallery               看进度
```

索引存在 `gallery.db`（SQLite），不是 JSON —— 一万条记录约 1.3 MB，两词检索约 1 ms。用 JSON 的话每索引一张就要全量重写整个文件，跑一万张等于几十 GB 的无谓 IO。

| 指令 | 用法 |
|---|---|
| `/gallery` | 看状态：已登记 / 已索引 / 待索引 / 分类数 |
| `/gallery scan` | 扫描目录登记新文件，幂等，可反复跑 |
| `/gallery index [N]` | 批量索引，默认 20 张，最多 200 |
| `/gallery search <词>` | 手动测检索效果 |
| `/gallery retry` | 清零失败计数，重跑失败的图 |
| `/photo g123 [附言]` | 手动发一张，不受冷却和每日上限约束 |

### 目录结构

顶层子文件夹名即分类，她挑图时可以按分类筛：

```
/AstrBot/data/pics/gallery/
├── 博主A/          ← 分类名就是文件夹名
│   ├── 001.jpg
│   └── 002.jpg
├── 博主B/
└── 日常/
```

递归扫描，支持 jpg / jpeg / png / webp，非图片文件自动忽略。

> ⚠️ **检索是按词面匹配的。** 视觉模型默认会写「黑色丝袜」，而你搜的是「黑丝」——匹配不上。内置提示词已经要求它把口语简称一并写进描述（`黑色丝袜（黑丝）`），**自己改 `vision_prompt` 时务必保留这一条**，否则索引跑完了才发现搜不到，就得全部重跑。

## 安装前的准备

### 1. 建频道（发动态功能必需）

1. Telegram 里新建一个频道，设为私密
2. 把你的 bot 加为管理员，勾选「发布消息」权限
3. 拿到频道 ID：从频道转发任意一条消息给 `@userinfobot`，它会告诉你数字 ID（`-100` 开头）
4. 把这个 ID 填进插件配置的 `channel_id`

公开频道也可以直接填 `@频道用户名`。

### 2. 准备图片目录（可选）

两个目录都可以留空，对应功能会自动禁用。

**头像目录 `avatar_dir`**
- **只会读取 `.jpg` / `.jpeg`** —— Telegram 头像接口只收 JPEG，png 会被忽略
- 可以建子文件夹作为分类，子文件夹名就是角色调用时能指定的 `category`

**动态配图目录 `moment_photo_dir`**
- 支持 `.jpg` / `.jpeg` / `.png` / `.webp`
- 同样支持子文件夹分类

Docker 部署建议放在挂载卷里，例如：

```
/AstrBot/data/pics/avatars/日常/
/AstrBot/data/pics/avatars/出门/
/AstrBot/data/pics/moments/风景/
```

配置里填容器内的绝对路径。

## 配置项

### 频道与频率

| 配置项 | 默认 | 说明 |
|---|---|---|
| `channel_id` | 空 | 动态频道 ID。留空则禁用发动态 |
| `post_cooldown_minutes` | 180 | 两条动态最短间隔。**0 = 不限制** |
| `post_daily_limit` | 5 | 每日动态上限。**0 = 不限制** |
| `avatar_cooldown_minutes` | 720 | 换头像最短间隔。**0 = 不限制** |

> **冷却和每日上限只约束角色的自主行为，不约束你的手动指令。**
> `/moment` `/avatar` 任何时候都能用，不受冷却和上限影响，也不消耗当天配额、不重置冷却计时。
> 手动发的动态仍然会记进历史，角色能看到自己频道上有这条。

冷却或上限触发时，工具会返回一句给角色看的话（如"现在还发不了动态，距离上一条还差 47 分钟"），角色知道发不成也知道原因，不会反复重试。

### 历史动态注入

角色需要记得自己发过什么，否则会重复发相似内容。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `inject_history` | 开 | 每次对话前注入历史动态的文字 |
| `inject_history_limit` | 0 | 注入条数上限。**0 = 全部注入** |
| `inject_history_images` | 关 | 是否连配图一起注入。显著增加 token 和延迟 |
| `inject_images_limit` | 10 | 配图张数上限。0 = 不限制（不建议） |

### 图片记忆

| 配置项 | 默认 | 说明 |
|---|---|---|
| `describe_images` | 开 | 让角色自己写目录层描述（`<img_note>`），不额外调模型 |
| `max_context_images` | 0 | 上下文里最多留几张真图，更早的折叠成占位。**0 = 不折叠** |
| `vision_max_chars` | 600 | 细节记录存档时的截断长度 |
| `vision_concurrency` | 2 | 视觉解析并发数，一次涌入多张图时靠它限流 |

### 独立视觉 API

细节层用的是插件自己的 API 配置，跟 AstrBot 的服务提供商无关。**地址、Key、模型 ID 都填了才启用。**

| 配置项 | 默认 | 说明 |
|---|---|---|
| `vision_api_format` | `openai` | 接口格式：`openai` / `anthropic` / `gemini`。**必须选对**，三家的请求体和鉴权头完全不同 |
| `vision_base_url` | 空 | 只填到根即可，插件按格式补路径；填全了也认 |
| `vision_api_key` | 空 | 鉴权头按格式自动选 |
| `vision_model` | 空 | 必须是支持图片输入的多模态模型 |
| `vision_stream` | 关 | 流式接收。**只在网关对非流式长响应 504 时才需要开** |
| `vision_context_window` | 128000 | 该模型的上下文窗口。**不会发给 API**，仅用于校验下面那项 |
| `vision_max_tokens` | 1024 | 输出上限。接近窗口时会被自动压到窗口的 1/4 并警告 |
| `vision_system_prompt` | 空 | system 角色。留空用内置的（只输出客观描述、不加开场白和免责声明） |
| `vision_prompt` | 空 | user 消息，和图片一起发。留空用内置的 |
| `vision_extra_body` | 空 | 一段 JSON，合并进请求体顶层。用来填插件没做成配置项的参数 |

#### 三种格式怎么填

用中转站的话基本都是 `openai`，除非它明确说自己转发原生格式。

| 格式 | 地址填 | 补成 | 鉴权头 | 模型名举例 |
|---|---|---|---|---|
| `openai` | `https://api.openai.com/v1` | `…/v1/chat/completions` | `Authorization: Bearer` | `gpt-4o-mini`、`qwen-vl-max` |
| `anthropic` | `https://api.anthropic.com` | `…/v1/messages` | `x-api-key` + `anthropic-version` | `claude-haiku-4-5` |
| `gemini` | `https://generativelanguage.googleapis.com/v1beta` | `…/models/{模型}:generateContent` | `x-goog-api-key` | `gemini-2.5-flash` |

Gemini 的 Key 走**请求头**而不是 `?key=` URL 参数 —— 免得密钥出现在 URL 里被各级日志抄走。模型名会拼进路径，所以直接写 `gemini-2.5-flash`，不要写成 `models/gemini-2.5-flash`。

配好后用 **`/vision test`** 拿一张真图跑一次完整请求，直接看通不通 —— 比发张图然后翻日志快得多。它会先回显解析出的格式、模型和最终地址，配错了一眼能看出来。

#### `vision_extra_body`

插件只做了通用的那几项，其余参数从这里塞进去，按你选的格式写。合并规则：同名的字典合并，其余直接覆盖。

Gemini 放宽内容过滤（图像描述被误拦时用）：

```json
{"safetySettings": [
  {"category": "HARM_CATEGORY_SEXUALLY_EXPLICIT", "threshold": "BLOCK_NONE"},
  {"category": "HARM_CATEGORY_DANGEROUS_CONTENT", "threshold": "BLOCK_NONE"}
]}
```

OpenAI 格式调采样：`{"temperature": 0.3}`。

> **`vision_context_window` 的作用有限**，如实说明：单次请求只有一张图加一段短提示词，上下文窗口基本不构成约束，所以它只用来挡「最大输出长度设得比窗口还大」这种配置错误。没有拿它做别的事。

> **`vision_stream` 默认关是有意的。** 结果整体存档，没人盯着看逐字输出，流式在这里唯一的价值是**绕过网关超时** —— 有些中转站对非流式的长响应直接 504 或挂断，那种情况下只有流式能跑通。插件会把增量拼回完整文本再存，三种格式的 SSE 结构不同（Anthropic 的 `content_block_delta`、Gemini 的 `candidates[].content.parts[]`、OpenAI 的 `choices[].delta.content`），都已分别处理，推理模型的 thinking 增量会被丢掉。

### 其他

| 配置项 | 默认 | 说明 |
|---|---|---|
| `enable_reaction` | 开 | 是否允许角色打表情 |
| `timezone` | Asia/Shanghai | 用于每日上限的自然日边界和时间戳显示 |
| `admin_only_commands` | 开 | 手动指令是否仅管理员可用 |

> `admin_only_commands` 建议保持开启。头像是 **bot 全局设置**，任何人改都会影响所有用户看到的资料。

## 指令

| 指令 | 用法 |
|---|---|
| `/moment <正文>` | 手动发一条动态，可在同一条消息里附带图片 |
| `/avatar [分类]` | 手动换头像，分类可省略 |
| `/presence` | 查看已发动态数、各项冷却、图片存档统计 |
| `/gallery [scan\|index N\|search 词\|retry]` | 管理相册索引，见 [发照片](#发照片) |
| `/photo <编号> [附言]` | 手动发一张照片。`g123` 相册里的，`#3` 聊过的旧图 |
| `/vision [张数\|retry\|test]` | 给还没有细节记录的存量图片补做解析。默认一次 10 张；`test` 拿一张真图测连通；`retry` 清空失败计数重来 |

表情回应没有指令入口 —— 它需要"对方刚发的那条消息"作为目标，指令场景下没有意义。

## 建议的验证顺序

装好后先用指令验证底层通路，再看角色会不会自己调：

1. `/presence` —— 能返回状态说明插件加载成功
2. `/moment 测试动态` —— 验证频道 ID 和管理员权限
3. `/moment 带图测试` + 附一张图 —— 验证附带图片的取用
4. `/avatar` —— 验证 ptb 版本和 JPEG 目录
5. 正常聊天，观察角色是否自主调用

### 图片记忆的验证顺序

这块有先后依赖，**别一次全开**：

1. 保持 `max_context_images = 0`，正常聊天时发几张图
2. 日志里搜 `收到 N 条图片描述` —— 确认目录层在工作
3. 确认 `<img_note>` **没有漏到 Telegram 聊天窗口**
4. 填好视觉 API 三项，`/vision test` 确认能通
5. `/vision` 给之前的存量图片补细节记录
6. `/presence` 看三个数字对不对得上（存档张数 / 描述条数 / 细节条数）
7. 以上都正常，再把 `max_context_images` 改成正数开始折叠

第 7 步之前折叠不会发生。**顺序反了的话，图片会在还没有任何描述时就被折叠成 `[图片 #N · 时间 · 已折叠]`，那张图就再也认不出来了**（原图还在，但没有能检索的文字）。真发生了可以用 `/vision` 补细节层，目录层补不回来。

## 已知限制

**头像是全局的。** `setMyProfilePhoto` 改的是 bot token 本身的资料，**不是按用户区分的**。角色因为和 A 聊天换了头像，所有用户都会看到。如果这个 bot 服务多个用户，建议保持 `admin_only_commands` 开启，或者一段关系用一个独立 bot。

**收不到你的反应。** 你在频道给动态点了表情，角色不会知道 —— Telegram 的 `message_reaction` 更新需要额外配置，AstrBot 适配器目前不转发。设计上是单向的：她发，你看，想说什么私聊里说。

**接口频率未公布。** Telegram 官方没有公布 `setMy*` 系列的调用频率上限，超限会返回 429。这就是插件默认给了较长冷却时间的原因，别把冷却全设成 0。

**头像不能复用。** Telegram 明确禁止用 `file_id` 复用头像，每次都是重新上传。

## 排障

插件所有日志都带 `[tg_presence]` 前缀，在「平台日志」里搜这个即可。

| 现象 | 检查 |
|---|---|
| 指令没反应 | 插件是否启用；`admin_only_commands` 开着而你不是管理员 |
| 换头像报版本太低 | `docker exec astrbot pip show python-telegram-bot`，需要 >= 22.7 |
| 发动态失败 | 频道 ID 是否正确；bot 是否是频道管理员且有发布权限 |
| 找不到图片 | 路径是否为**容器内**绝对路径；头像目录里是否有 jpg（png 不算） |
| 附带图片没被用上 | 日志里搜 `附带图片取路径失败` |
| 表情回应失败 | 日志里搜 `取不到 message_id` |
| `<img_note>` 漏到聊天窗口 | v0.11.0 及以前的已知缺陷，升级到 v0.11.1。仍然出现的话日志里搜 `发送前兜底剥掉` |
| 一直没有图片描述 | 日志里搜 `请求描述图片`；没有则说明上下文里没检测到图片。也可能是同一个 v0.11.0 缺陷——抽取和剥离是同一段代码，一起失效 |
| 视觉解析不跑 | `/vision` 会告诉你三项配置缺哪个、有多少张待解析 |
| 视觉解析一直失败 | `/vision test` 直接测，它会回显格式和最终地址。401/403 = Key 错**或格式选错**，404 = 地址或模型 ID 错，400 看日志里的报错正文 |
| 报错说字段不认识 | 格式选错了 —— 拿 `openai` 的请求体发给 Anthropic 端点必然报字段错 |
| 视觉解析返回空 | 模型拒答或触发内容过滤。改 `vision_system_prompt`；Gemini 可用 `vision_extra_body` 放宽 `safetySettings` |
| 网关 504 / 连接被挂断 | 开 `vision_stream` |
| 连续 3 次失败后不再重试 | 这是设计如此，避免坏图无限撞 API。修好配置后用 `/vision retry` |

## 状态存储

```
/AstrBot/data/plugin_data/astrbot_plugin_tg_presence/
├── state.json          动态记录、冷却、每日计数、图片编号/路径/时间/目录层描述
├── vision.json         细节层（视觉模型写的画面记录）
├── gallery.db          相册索引（SQLite）：路径、分类、描述、发送次数
├── moment_photos/      动态里附带的图片
└── context_photos/     从对话上下文里存下来的图片原图
```

细节层单独放一个文件，是因为 `state.json` 每发一条动态、每次冷却都要全量重写 —— 混在一起等于每次把几百张图的详解也抄一遍。

- 删掉 `state.json`：清空历史动态记录（频道里已发的消息不受影响）、所有冷却状态，以及图片编号表。**编号表没了之后，`context_photos/` 里的图和 `vision.json` 里的记录就对不上了**
- 删掉 `vision.json`：清空细节层，`/vision` 可以重建
- 删掉 `context_photos/`：原图没了，`recall_photo` 失效，但两层文字描述还在，`find_photo` 和 `inspect_photo` 照常工作
