# 角色 Telegram 存在感（tg_presence）

给 Telegram 上的 AI 角色一层"生活痕迹"：她有自己的频道会发动态，会换头像、改签名，会给你的消息打表情，会记得你发过的每一张图、也会主动挑一张发给你。

行为能力全部注册为 **LLM 工具**，由角色自己决定什么时候用；每项也都保留手动指令入口。

> 仅支持 Telegram。需要 AstrBot >= 4.26；换头像需要 python-telegram-bot >= 22.7，其余功能不受此限。

## 能做什么

| 能力 | 说明 | 入口 |
|---|---|---|
| 发动态 | 往自己的频道发一条动态，可带配图。频道是真正的时间线，能往回翻、有推送 | LLM 自主 / `/moment` |
| 换头像 | 从候选目录里挑一张 JPEG 换上 | LLM 自主 / `/avatar` |
| 改签名 | 资料页上那句会变的话，点开她的头像就能看到 | LLM 自主 / `/signature` |
| 表情回应 | 给你刚发的消息打一个表情，不说话也让你知道她看到了 | LLM 自主 |
| 图片记忆 | 把上下文里的图换成可检索的文字，省 token 又不失忆 | LLM 自主 / `/vision` |
| 发照片 | 从相册里挑一张发给你，也能重发聊过的旧图 | LLM 自主 / `/photo` |
| 导演模式 | 用第二个 bot 当控制台，让她说话而你的指令不进你俩的聊天 | `/say` / `/act` |

九个 LLM 工具：`post_moment`、`change_avatar`、`update_signature`、`react_message`、`find_photo`、`inspect_photo`、`recall_photo`、`browse_gallery`、`send_photo`。

## 快速开始

最小可用只需要一步：建频道、填 `channel_id`，她就能发动态了。其余按需开。

```
1. 建频道 → 把 bot 设为管理员 → 拿到频道 ID → 填 channel_id
2. /presence        确认插件活着
3. /moment 测试     验证频道权限
```

完整能力的推荐开启顺序（每步都能独立验证）：

| 顺序 | 做什么 | 依赖 |
|---|---|---|
| 1 | 频道 + `channel_id` | — |
| 2 | 头像目录 + `avatar_dir` | ptb ≥ 22.7 |
| 3 | 视觉 API 四项 + `/vision test` | — |
| 4 | 相册目录 + `/gallery scan` + `/gallery index` | 第 3 步 |
| 5 | 图片记忆（`describe_images` → `max_context_images`） | 见[验证顺序](#验证顺序不能跳) |
| 6 | 第二个 bot + `director_platform_id` + `/link` | — |

## 发动态

### 为什么用频道而不是简介

Telegram bot 的「简介」（`setMyDescription`）**只在你还没和它对话过时显示一次**，聊过之后永远看不到。角色改了也没人看得见。

频道则是真正的时间线：一条条累积、能往回翻、有推送通知——行为上接近朋友圈。资料页上那句会变的话用的是另一个接口（`setMyShortDescription`），见[头像与签名](#头像与签名)。

### 配图从哪来

发动态时按这个顺序取图：

1. **当前消息里附带的图片**（优先）——你发 `/moment 今天天气真好` 并在同一条消息里附几张图，这些就是配图。她自主调用时同理：你发张图说「帮我发到频道」，那些图会被带上
2. **配图目录**（回退）——消息里没带图时，才按 `category` 从 `moment_photo_dir` 里随机挑

一次最多 10 张（Telegram 媒体组上限）。单张走 `sendPhoto`，多张走 `sendMediaGroup`。正文超过 1024 字符时塞不进 caption，插件会先发图、再补一条纯文字。

附带的图片会被拷进插件数据目录长期保存——平台的临时目录会被清理，而历史动态注入可能很久以后才读它。动态配图同时会登记进相册库，之后能被翻到、也能重新发给你。

### 说不说，什么时候说

`post_moment` 有个 `mention_now` 参数，决定发完要不要在聊天里主动提这件事。真人不是每条动态都会特意说一嘴——想让你立刻知道就传 true，想让你自己刷到、或者这条她暂时不想解释，就传 false 然后正常聊别的。

### 她记得自己发过什么

每次对话前会把历史动态按时间戳插进上下文，和聊天记录穿插在同一条时间线上，而不是附在末尾当成一份清单。所以她知道"那条动态是前天下午发的，当时我们正在聊……"。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `inject_history` | 开 | 注入历史动态文字 |
| `inject_history_limit` | 0 | 注入条数上限。**0 = 全部** |
| `inject_history_images` | 关 | 是否连配图一起注入。显著增加 token 和延迟 |
| `inject_images_limit` | 10 | 配图张数上限 |

### 频率

| 配置项 | 默认 | 说明 |
|---|---|---|
| `post_cooldown_minutes` | 180 | 两条动态最短间隔。**0 = 不限** |
| `post_daily_limit` | 5 | 每日上限。**0 = 不限** |

> **冷却和每日上限只约束她的自主行为，不约束你的手动指令。** `/moment` 任何时候都能用，不消耗当天配额、不重置冷却计时。手动发的仍会记进历史，她能看到自己频道上有这条。

触发限制时工具会返回一句给她看的话（如"现在还发不了动态，距离上一条还差 47 分钟"），她知道发不成也知道原因，不会反复重试。

## 头像与签名

**头像**从 `avatar_dir` 里随机挑，**只读 `.jpg` / `.jpeg`**——Telegram 头像接口只收 JPEG，png 会被忽略。可以建子文件夹作为分类，子文件夹名就是她调用时能指定的 `category`。

**签名**是资料页上那句会变的话（`setMyShortDescription`，120 字符以内），点开她的头像就能看到。它会覆盖上一句、没有历史记录，所以适合放此刻的状态或心情；想记录某件事、想让你收到通知，那是动态的活儿。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `avatar_dir` | 空 | 候选头像目录，绝对路径。留空禁用 |
| `avatar_cooldown_minutes` | 720 | 换头像最短间隔 |
| `signature_cooldown_minutes` | 360 | 改签名最短间隔 |

> 头像和签名都是 **bot 全局设置**，不是按用户区分的。她因为和 A 聊天换了头像，所有用户都会看到。多用户场景建议保持 `admin_only_commands` 开启，或者一段关系用一个独立 bot。

## 图片记忆

### 要解决的问题

AstrBot 把图片以 base64 **永久写进对话历史**，之后每一轮都原样重发。几十张之后上下文里全是图片，既烧 token 又稀释注意力——模型的有效注意力被一堆不相关的旧图分走了。

但直接删掉又不行：你会说「昨天那张」「黑丝那张」，她得认得出来。

所以这里的做法是**把图片换成文字，留在时间线上**。

### 两层描述

一张图存两份文字，用途不同：

| 层 | 谁写的 | 长度 | 内容 | 存在哪 |
|---|---|---|---|---|
| **目录层** | 主模型（她自己） | 一句话 | 她的视角和当时的语境：「阿泽昨天加班时拍的」 | `state.json` |
| **细节层** | 独立视觉模型 | 几百字 | 客观画面：构图、衣着材质颜色、物品、文字、光线 | `vision.json` |

**目录层**跟正文一次生成——上下文里出现没描述过的图时，插件注入一段请求，她在回复末尾附 `<img_note id="3">…</img_note>`，插件抽走存档并从要发出去的内容里剥掉，你看不到。不额外调模型，而且此刻她正看着图、也知道当时在聊什么，写出来的话带着她自己的说法。一轮最多请求 5 条，多了模型容易敷衍或写到一半被截断。

**细节层**在图片首次进入上下文时**异步**调视觉 API 解析，不阻塞回复。

两层的价值在于**信息类型不同，不只是详略不同**。你说「昨天加班那张」走目录层，说「有咖啡杯那张」走细节层。而且能跨层组合：「加班 咖啡杯」——「加班」在目录、「咖啡杯」在细节，照样命中。

### 检索

| 工具 | 做什么 | 代价 |
|---|---|---|
| 看占位 | 折叠后的 `[图片 #3 · 07-31 14:30 · 阿泽拍的，穿黑丝踩高跟 · 已折叠]` 就在对话里，读一眼就认出来 | 零 |
| `find_photo` | 按关键词 + 日期搜存档，两层一起搜 | 一次工具调用 |
| `inspect_photo` | 查某张图的画面细节，**只回文字** | 一次工具调用 |
| `recall_photo` | 把原图整个塞回上下文重新看 | 一张图的 token |

顺序是有讲究的：占位就在眼前，不需要检索；`find_photo` 查的是存档、不依赖上下文，所以对话压缩掉占位后它照样能找到；`inspect_photo` 回答「那张图里有什么」而不用重新传图，比 `recall_photo` 便宜一个数量级。

**候选不止一张时，提示词要求她反问是哪张，而不是自己挑一张当成就是那张。**

> `recall_photo` 是让她**自己再看一眼**，不是发给你。要把图发给你是 [`send_photo`](#发照片)。

### 上下文瘦身

`max_context_images` 设成正数后，只保留最近 N 张真图，更早的换成文字占位。

> ⚠️ **折叠会写回对话历史，不可逆。** 但图片在首次进入上下文时就已存到 `context_photos/` 下，原图不会丢，`recall_photo` 随时能取回。

### 验证顺序（不能跳）

这块有先后依赖，**别一次全开**。默认 `max_context_images = 0`，也就是不折叠——先把描述链路跑通再开。

```
1. 保持 max_context_images = 0，正常聊天时发几张图
2. 日志里搜「收到 N 条图片描述」        ← 目录层在工作
3. 确认 <img_note> 没有漏到聊天窗口
4. 填好视觉 API，/vision test 确认能通
5. /vision 给之前的存量图片补细节记录
6. /presence 看三个数字对得上（存档 / 描述 / 细节）
7. 以上都正常，再把 max_context_images 改成正数
```

**顺序反了的话，图片会在还没有任何描述时就被折叠成 `[图片 #N · 时间 · 已折叠]`，那张图就再也认不出来了**（原图还在，但没有能检索的文字）。细节层事后能用 `/vision` 补，**目录层补不回来**——那句带语境的话只有在她当时看着图的时候才写得出来。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `describe_images` | 开 | 让她自己写目录层描述，不额外调模型 |
| `max_context_images` | 0 | 上下文里最多留几张真图。**0 = 不折叠** |
| `vision_max_chars` | 600 | 细节记录存档时的截断长度 |
| `vision_concurrency` | 2 | 视觉解析并发数 |

## 发照片

她能主动发照片给你，图从两处来：

| 来源 | 编号 | 说明 |
|---|---|---|
| **相册目录** | `g123` | `gallery_dir` 下的图，扫描登记 + 视觉索引后可按画面内容检索 |
| **聊过的旧图** | `#3` | 之前出现在对话里的图，随时能重发 |

动态的配图在发出时自动登记进相册库，所以也能被翻到、被重发。

| 工具 | 做什么 |
|---|---|
| `browse_gallery(keywords, folder)` | 在相册里翻，返回候选 `g123` 列表。不带关键词就是随手翻翻 |
| `send_photo(photo_id, caption)` | 发出去。`g123` 相册里的，`#3` 聊过的旧图 |

检索结果里**最近发过的排在最后**，避免反复发同一张。

### 目录结构

顶层子文件夹名即分类，她挑图时可以按分类筛：

```
/AstrBot/data/pics/gallery/
├── 博主A/          ← 分类名就是文件夹名
│   ├── 001.jpg
│   └── 002.jpg
├── 博主B/
└── 日常/
```

递归扫描，支持 jpg / jpeg / png / webp，非图片文件自动忽略。

### 建索引

上万张图不可能塞进上下文，得先建一份可检索的索引。分两步，都能中断续跑：

```
/gallery scan          扫目录登记路径（不调 API，几秒到几十秒）
/gallery index 10      ← 先跑 10 张
/gallery search 黑丝    ← 验证！看描述里有没有口语简称
/gallery index 200     确认没问题再放量，重复到跑完
```

> ⚠️ **第三步别跳过。检索是按词面匹配的。** 视觉模型默认会写「黑色丝袜」，而你搜「黑丝」——匹配不上，这张图就永远找不到。内置提示词已经要求它把口语简称一并写进描述（`黑色丝袜（黑丝）`），**自己改 `vision_prompt` 时务必保留这一条**。一万张跑完才发现搜不到，就得 `/gallery retry` 全部重来。

索引存在 `gallery.db`（SQLite）。一万条记录约 1.3 MB，两词检索约 1 ms。

| 指令 | 用法 |
|---|---|
| `/gallery` | 看状态：已登记 / 已索引 / 待索引 / 分类数 |
| `/gallery scan` | 扫描目录登记新文件，幂等，可反复跑 |
| `/gallery index [N]` | 批量索引，默认 20 张，最多 200 |
| `/gallery search <词>` | 手动测检索效果 |
| `/gallery retry` | 清零失败计数，重跑失败的图 |
| `/photo <编号> [附言]` | 手动发一张，不受冷却和每日上限约束 |

| 配置项 | 默认 | 说明 |
|---|---|---|
| `gallery_dir` | 空 | 相册目录，绝对路径。留空禁用发照片 |
| `photo_cooldown_minutes` | 10 | 两张照片最短间隔。真人不会连着刷图 |
| `photo_daily_limit` | 20 | 每日上限 |

## 导演模式

你想让她说点什么，但**不希望这条指令出现在你俩的聊天里**。用第二个 bot 当控制台：

```
你 ──/act 跟他说你今天加班到很晚──▶ 控制台 bot
                                      │
                                角色 bot ─────▶ 你
                                （只有她发的这条进上下文）
```

指令走的是另一条会话，所以既不进她的 LLM 上下文，也不出现在你俩的 Telegram 聊天窗口里。她的对话历史里只会多出她自己发的那条。

> 普通指令用的 `should_call_llm` 只能让消息不进 LLM 上下文，那条 `/moment xxx` 仍然躺在聊天记录里看得见。要彻底隐身只能走独立通道。

| 指令 | 做什么 |
|---|---|
| `/say <原话>` | 她原样发出这句。不调模型，你写什么她发什么 |
| `/act <提示>` | 你给方向，她带着人格和最近的对话自己组织语言再发 |

`/act` 更像那么回事——`/act 跟他说你今天加班到很晚，有点累` 出来的是她的语气和分段习惯，不是你的措辞。

### 配置

1. AstrBot 里再接一个 Telegram bot，记下它的**适配器实例 ID**（平台配置里那个名字，不是 bot 用户名）
2. 填进 `director_platform_id`
3. **在角色的私聊里**发一次 `/link`——绑定投递目标
4. 之后在控制台 bot 里 `/say` / `/act`

`/link` 必须在角色那边发（要绑的是她和你的会话），`/say` `/act` 必须在控制台发（在她那边发等于当着她的面喊话）——两个方向都有拦截。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `director_platform_id` | 空 | 控制台 bot 的适配器 ID。留空禁用 |
| `director_context_turns` | 40 | `/act` 生成时往前带多少条历史 |

> 发出去的话会写进她的对话历史（带时间戳，跟随 `stamp_own_messages`）。**这一步不能省**——否则她下一轮不知道自己说过这句，会接不上茬：你让她说"今天加班到很晚"，五分钟后她可能问你"你今天忙吗"。写失败时返回里会明确告知。

## 视觉 API

细节层和相册索引都用它。这套配置**在插件里独立填**，不走 AstrBot 的服务提供商——主对话模型贵、这个便宜，本来就不该共用一套配置，也不该让它出现在对话模型的候选列表里。

建议挑个便宜的多模态模型。上万张图跑一遍，用 Gemini Flash 这类大约几美元；用 Claude 或 GPT-4o 会贵一到两个数量级。

**地址、Key、模型 ID 都填了才启用。**

### 三种接口格式

`vision_api_format` **必须选对**，三家的请求体、鉴权头、图片包装方式完全不同。用中转站的话基本都选 `openai`，除非它明确说自己转发原生格式。

| 格式 | 地址填 | 补成 | 鉴权头 | 模型名举例 |
|---|---|---|---|---|
| `openai` | `https://api.openai.com/v1` | `…/v1/chat/completions` | `Authorization: Bearer` | `gpt-4o-mini`、`qwen-vl-max` |
| `anthropic` | `https://api.anthropic.com` | `…/v1/messages` | `x-api-key` + `anthropic-version` | `claude-haiku-4-5` |
| `gemini` | `https://generativelanguage.googleapis.com/v1beta` | `…/models/{模型}:generateContent` | `x-goog-api-key` | `gemini-2.5-flash` |

只填到根即可，插件按格式补路径；填全了也认。

Gemini 的 Key 走**请求头**而不是 `?key=` URL 参数——免得密钥出现在 URL 里被各级日志抄走。模型名会拼进路径，所以直接写 `gemini-2.5-flash`，不要写成 `models/gemini-2.5-flash`。

配好后用 **`/vision test`** 拿一张真图跑一次完整请求，直接看通不通。它会先回显解析出的格式、模型和最终地址，配错了一眼能看出来。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `vision_api_format` | `openai` | `openai` / `anthropic` / `gemini` |
| `vision_base_url` | 空 | 接口地址 |
| `vision_api_key` | 空 | 鉴权头按格式自动选 |
| `vision_model` | 空 | 必须支持图片输入 |
| `vision_stream` | 关 | 流式接收，见下 |
| `vision_context_window` | 128000 | 模型的上下文窗口。**不会发给 API** |
| `vision_max_tokens` | 1024 | 输出上限。接近窗口时自动压到 1/4 并警告 |
| `vision_system_prompt` | 空 | system 角色。留空用内置的 |
| `vision_prompt` | 空 | user 消息，和图片一起发。留空用内置的 |
| `vision_extra_body` | 空 | 一段 JSON，合并进请求体顶层 |

### 两个提示词的分工

**system** 管态度：只输出客观描述、不加开场白、不加免责声明。模型总是拒答或者总在描述前后加废话时，改这里——那是 system 层的事，写在 user 提示词里按不住。

**解析提示词** 管内容清单：要覆盖哪些方面（衣着材质颜色、画面文字、光线、色调、口语简称）。

出问题时对号入座：模型不肯描述 / 总加废话 → 改 system；描述内容不对、漏了你要的东西 → 改解析提示词。

### `vision_extra_body`

插件只做了通用的那几项，其余参数从这里塞进去，按你选的格式写。合并规则：同名的字典合并，其余直接覆盖。

Gemini 放宽内容过滤（图像描述被误拦时用）：

```json
{"safetySettings": [
  {"category": "HARM_CATEGORY_SEXUALLY_EXPLICIT", "threshold": "BLOCK_NONE"},
  {"category": "HARM_CATEGORY_DANGEROUS_CONTENT", "threshold": "BLOCK_NONE"}
]}
```

OpenAI 格式调采样：`{"temperature": 0.3}`。

### 关于两个容易误解的开关

**`vision_context_window` 的作用有限**，如实说明：单次请求只有一张图加一段短提示词，上下文窗口基本不构成约束，所以它只用来挡「最大输出长度设得比窗口还大」这种配置错误。没有拿它做别的事。

**`vision_stream` 默认关是有意的。** 结果整体存档，没人盯着看逐字输出，流式在这里唯一的价值是**绕过网关超时**——有些中转站对非流式的长响应直接 504 或挂断，那种情况下只有流式能跑通。插件会把增量拼回完整文本再存，三种格式的 SSE 结构不同，都已分别处理，推理模型的 thinking 增量会被丢掉。

## 数据存储

```
/AstrBot/data/plugin_data/astrbot_plugin_tg_presence/
├── state.json          动态记录、冷却、每日计数、图片编号/路径/时间/目录层描述
├── vision.json         细节层（视觉模型写的画面记录）
├── gallery.db          相册索引（SQLite）：路径、分类、描述、发送次数
├── moment_photos/      动态里附带的图片
└── context_photos/     从对话上下文里存下来的图片原图
```

细节层和相册索引都单独存，是因为 `state.json` 每发一条动态、每次冷却都要全量重写——混在一起等于每次把几百张图的详解也抄一遍。相册用 SQLite 而不是 JSON，则是因为批量索引时每张图都要落盘，全量重写一万次是几十 GB 的无谓 IO。

- 删掉 `state.json`：清空动态记录（频道里已发的消息不受影响）、冷却状态、图片编号表。**编号表没了之后，`context_photos/` 里的图和 `vision.json` 里的记录就对不上了**
- 删掉 `vision.json`：清空细节层，`/vision` 可重建
- 删掉 `gallery.db`：清空相册索引，`/gallery scan` + `/gallery index` 可重建（要重新花一遍 API 钱）
- 删掉 `context_photos/`：原图没了，`recall_photo` 和 `#N` 发图失效，但两层文字描述还在，检索照常

## 排障

所有日志都带 `[tg_presence]` 前缀，在「平台日志」里搜这个即可。

| 现象 | 检查 |
|---|---|
| 指令没反应 | 插件是否启用；`admin_only_commands` 开着而你不是管理员（对照 `admins_id` 和你真实的 Telegram 用户 ID） |
| 换头像报版本太低 | `docker exec astrbot pip show python-telegram-bot`，需要 ≥ 22.7 |
| 发动态失败 | 频道 ID 是否正确；bot 是否是频道管理员且有发布权限 |
| 找不到图片 | 路径是否为**容器内**绝对路径；头像目录里是否有 jpg（png 不算） |
| 附带图片没被用上 | 日志搜 `附带图片取路径失败` |
| 表情回应失败 | 日志搜 `取不到 message_id` |
| `<img_note>` 漏进聊天窗口 | 日志搜 `发送前兜底剥掉`——出现即说明第一道剥离失效了 |
| 一直没有图片描述 | 日志搜 `请求描述图片`；没有则说明上下文里没检测到图片 |
| 视觉解析不跑 | `/vision` 会告诉你三项配置缺哪个、有多少张待解析 |
| 视觉解析一直失败 | `/vision test` 直接测，它会回显格式和最终地址。401/403 = Key 错**或格式选错**，404 = 地址或模型 ID 错，400 看日志里的报错正文 |
| 报错说字段不认识 | 格式选错了——拿 `openai` 的请求体发给 Anthropic 端点必然报字段错 |
| 视觉解析返回空 | 模型拒答或触发内容过滤。改 `vision_system_prompt`；Gemini 可用 `vision_extra_body` 放宽 `safetySettings` |
| 网关 504 / 连接被挂断 | 开 `vision_stream` |
| 连续 3 次失败后不再重试 | 设计如此，避免坏图无限撞 API。修好配置后 `/vision retry` 或 `/gallery retry` |
| 相册搜不到应该有的图 | 描述里可能只有正式说法。`/gallery search 黑色丝袜` 试试，命中就说明是口语简称没写进去 |
| `/act` 出来的话不像她 | 日志搜 `没拿到人格`——出现即说明生成时没带上人格 |
| `/say` `/act` 说不能在这儿发 | 那是拦截，得在控制台那个 bot 里发；`/link` 反过来必须在角色那边发 |

## 已知限制

**头像和签名是全局的。** `setMyProfilePhoto` / `setMyShortDescription` 改的是 bot token 本身的资料，不按用户区分。她因为和 A 聊天换了头像，所有用户都会看到。多用户场景建议一段关系一个独立 bot。

**收不到你的反应。** 你在频道给动态点了表情，她不会知道——Telegram 的 `message_reaction` 更新需要额外配置，AstrBot 适配器目前不转发。设计上是单向的：她发，你看，想说什么私聊里说。

**接口频率未公布。** Telegram 官方没有公布 `setMy*` 系列的调用频率上限，超限会返回 429。这就是默认给了较长冷却的原因，别把冷却全设成 0。

**头像不能复用。** Telegram 明确禁止用 `file_id` 复用头像，每次都是重新上传。

**对话压缩会吃掉占位。** AstrBot 的历史压缩会把折叠占位连同描述一起压掉。`find_photo` 查的是插件自己的存档、不受影响，但对话里那行 `[图片 #3 · … · 已折叠]` 会消失——她需要主动检索才能想起来，而不是一眼看到。

**图片记忆的目录层补不回来。** 细节层可以事后用 `/vision` 补，目录层不行——那句带语境的话只有在她当时看着图、也知道在聊什么的时候才写得出来。所以[验证顺序](#验证顺序不能跳)里那一步不能跳。
